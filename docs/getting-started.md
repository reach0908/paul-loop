# Paul Loop 처음 사용하기

Paul Loop는 개발·검증·리뷰·PR 작업을 하나의 이름으로 시작하는 플러그인이다. 작은 수정은
필요한 검사만 수행하고, PR까지 요청한 작업에는 해당 리뷰·게시 절차를 적용한다.

이 문서는 **통합 `paul-loop` 0.1.0 구조** 기준이다. [통합 PR #140](https://github.com/reach0908/paul-loop/pull/140)의
머지·릴리스 상태를 먼저 확인한다. 배포 전에는 아래 공개 설치 명령으로 통합 버전을 받을 수
있다고 가정하지 않는다. 이미 설치한 세 플러그인은 [전환 절차](unified-installation.md)를 따른다.

## 1. 설치하고 새 세션에서 시작하기

Node 22와 Bash 3.2+가 검증 기준이다. 사용하는 호스트 한 가지의 설치 절차를 선택한다.

| 호스트 | 설치 | 새 세션의 시작 명령 |
|---|---|---|
| Claude Code | 아래 marketplace 명령 | `/paul-loop:paul-loop` |
| Codex | [생성 패키지 설치 가이드](codex-installation.md)의 generate → plan → apply | `$paul-loop` |

통합 버전이 공개된 뒤 Claude 터미널에서 실행한다. 프로젝트 범위 설치 예시다.

```bash
claude plugin marketplace add reach0908/paul-loop
claude plugin install paul-loop@paul-loop --scope project
```

Codex는 provider 저장소 URL을 직접 등록하는 방식이 아니라 **생성된 Codex marketplace**를
설치한다. 기존 `zine-codex` 등 파생 설치와 새 플러그인의 훅을 동시에 켜지 않는다.
설치 후 실제 개발 프로젝트에서 새 세션을 열고 설치 목록·활성 상태를 확인한다.
설치 성공과 호스트의 훅 신뢰, 에이전트 역할 등록은 별도 상태다.

## 2. 프로젝트의 검증 명령 연결하기

먼저 이렇게 요청하면 된다.

> 폴루프로 이 프로젝트 설정을 확인하고, 기존 테스트와 검증 명령에 맞춰 연결해줘.

기존 `.claude/ship-flow.config.json` 파일 이름은 호환성을 위해 유지한다. 설정이 이미 있으면
검증 명령, issue tracker, 브랜치, 출력 언어를 보존한다. 처음부터 모든 설정을 새로 만들 필요는 없다.

셸 명령을 사용할 프로젝트는 [프로젝트 launcher·lock 가이드](project-installations.md)에 따라
검토한 `tools/paul-loop.mjs`와 독립적으로 승인한 패키지 핀을 준비한다. 그 뒤 프로젝트 루트에서:

```bash
node tools/paul-loop.mjs doctor
```

실제 설치의 버전·내용이 lock과 일치해야 한다. 실패하면 설치와 핀을 대조한다. 설치 캐시로부터
기대 해시를 새로 계산해 통과시키지 않는다. 단순 질문이나 작은 편집에는 전체 설정·DB 준비를
강요하지 않는다.

## 3. 평소에는 작업의 끝을 말하기

| 요청 예시 | 수행 범위 |
|---|---|
| “폴루프로 이 오류를 재현하고 수정해줘” | 원인 확인, 수정, 해당 검증 |
| “폴루프로 이 변경을 코드리뷰해줘” | 요청한 변경 리뷰 |
| “폴루프로 이 이슈를 구현하고 PR까지 만들어줘” | 구현, 필수 검증·리뷰, 허용된 게시 |
| “폴루프로 현재 상태만 확인해줘” | 읽기·진단·보고 |

메인 진입점에서 필요한 절차를 고르므로 `ship-flow`를 별도로 호출할 필요가 없다.
머지·배포·외부 메시지 전송에는 해당 행동에 대한 사용자의 권한이 필요하다. 검증 실패나
권한 부족은 완료로 보고하지 않는다.

## 4. 메모리는 필요한 단계까지만 쓰기

| 방식 | 준비 | 저장·조회되는 것 |
|---|---|---|
| 파일 교훈 | DB·API 키 불필요. 검증 근거를 갖춘 기록 절차 사용 | 프로젝트의 `.loop/lessons`와 FAIL→수정→PASS 근거 |
| 의미 검색 메모리 | 전용 pgvector DB, 임베딩 키, 서명 키, 명시적 활성화 | 검증된 교훈과 선택한 문서를 질문 의미에 맞춰 조회 |

파일 교훈도 설치만으로 모든 수정이 자동 기록되는 것은 아니다.
[검증된 수정 기록 절차](verified-lesson-workflow.md)에 따라 실제 실패와 수정 근거를 남긴다.
자연어로 유사한 문제를 찾을 필요가 생기면 [메모리 활성화 가이드](memory-guide.md)를 따른다.
플러그인이 전체 대화나 모든 프로젝트를 자동으로 영구 저장하는 것은 아니다.

## 5. 업데이트·끄기·문제 해결

- 설치 업데이트는 [호스트별 설치 가이드](unified-installation.md)와 [프로젝트 lock 갱신](project-installations.md)을
  함께 확인한다. provider 배포가 프로젝트 설치본까지 자동으로 바꾸지는 않는다.
- 의미 검색을 끄거나 “기억을 못 하는 것 같다”면 [메모리 확인·중지·문제 해결](memory-guide.md#6-새-세션에서-확인하기)을
  따른다. 이벤트 없음, 설정 누락, 검색 결과 없음은 서로 다르다.
- 원래 세 플러그인에서 옮길 때는 [기존 설치 전환](unified-installation.md#existing-installations)부터 한다.
  기존 설정과 `.loop/`를 지우지 않는다.

구현과 각 명령의 상세 계약은 [README의 모듈 참고자료](../README.md#whats-in-loop-engine)와
[런타임 호환성](runtime-compatibility.md)에 있다. `PASS`, 설치 성공, 검색 결과 존재는 각각 다른
증거이며, 실제 작업에 도움이 됐는지는 다음 자연스러운 재사용에서 확인한다.
